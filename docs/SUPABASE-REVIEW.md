## SECURITY DEFINER investigation
Supabase documents an rls_auto_enable function returning event_trigger to enable RLS for newly created tables. The name alone does not establish that the hosted definition is this example.
Default/inherited PUBLIC EXECUTE and Supabase role grants can make a SECURITY DEFINER function callable with its owner's privileges. The paired advisor checks concern anon and authenticated execution. Revoking only one direct grant can leave access through PUBLIC.
Return type matters: event-trigger functions cannot be invoked like ordinary functions, and the Data API may not expose that pseudotype. Do not claim a demonstrated arbitrary SQL exploit from the warning/name alone.
We have NOT read the hosted body or confirmed those exact advisor IDs. Required evidence: pg_get_functiondef, signature, return type, owner, proconfig, effective has_function_privilege for both roles, attached event triggers and API exposure.
supabase/review/rls-auto-enable-hardening.sql is a conditional, approval-only REVOKE proposal for the expected zero-argument SECURITY DEFINER event-trigger signature. It is NOT applied, not part of the application migration, and is not a verified fix. It aborts for unexpected signatures. Do not blindly drop the event trigger, change SECURITY DEFINER to INVOKER, or set search_path without reviewing its body.
After an approved fix: rerun advisors/effective privileges and verify privileged table creation still enables RLS. This is a production blocker until verified.
